# Reporte técnico de integración — Deployment ONNX

## 1. Propósito y alcance

Este directorio contiene un deployment autónomo del modelo base LightGBM convertido a ONNX. Está diseñado para integrarse en un software existente mediante ONNX Runtime, sin requerir LightGBM, scikit-learn, joblib ni el archivo original `.joblib`.

El paquete realiza:

- Normalización de una cotización.
- Consulta opcional del caché de rutas.
- Construcción de las 16 features numéricas.
- Ejecución de tres modelos ONNX.
- Transformación de logaritmos a MXN.
- Promedio del ensemble.
- Cálculo del intervalo técnico conservador.
- Entrega de metadatos de versión y auditoría.

El paquete no contiene:

- Interfaz web.
- Servidor HTTP o API.
- Autenticación.
- Conexión a la base Loadboard.
- Cliente de Google Maps.
- Política de margen o descuentos.
- Autorización comercial.
- Persistencia de cotizaciones.

Estado recomendado: `internal_beta`. El resultado es una precotización y no confirma disponibilidad ni tarifa de transportista.

## 3. Resumen del modelo original

| Propiedad | Valor |
|---|---|
| Familia | LightGBM tabular convertido a ONNX |
| Target de negocio | Costo total de transporte en MXN |
| Target técnico | `cost_mxn` |
| Transformación | `log1p(cost_mxn)` durante entrenamiento |
| Retorno a MXN | `expm1(predicción_log)` |
| Objetivo | `regression_l1` |
| Ensemble | Tres semillas: 42, 2026 y 9001 |
| Combinación | Promedio de las tres predicciones después de `expm1` |
| Ventana final | Nueve meses |
| Entrenado hasta | 31 de diciembre de 2025 |
| Decaimiento temporal | Semivida de 180 días |
| Trimming | Percentiles 0.5% y 99.5% dentro del entrenamiento |
| ONNX opset | 15 |
| Input ONNX | `float32 [N,16]` con nombre `features` |
| Versión | `lightgbm-base-2026.01-onnx-beta` |

El objetivo L1 y la transformación logarítmica implican que la salida central se interpreta como una aproximación al costo mediano condicional. No es una media garantizada ni una tarifa confirmada.

## 4. Variables utilizadas durante el entrenamiento

### 4.1 Variables crudas disponibles al cotizar

| Variable | Tipo | Descripción |
|---|---|---|
| `CLIENTE_key` | Categórica | Cliente normalizado |
| `PROVEEDOR_key` | Categórica | Proveedor; admite `__MISSING__` |
| `ORIGEN_key` | Categórica | Origen normalizado |
| `DESTINO_key` | Categórica | Destino normalizado |
| `route_key` | Categórica derivada | Ruta dirigida `origen -> destino` |
| `Tipo de Equipo_key` | Categórica | Equipo homologado |
| `DIVISION_key` | Categórica | División normalizada |
| `RANGO_key` | Categórica | Rango operativo normalizado |
| `route_type` | Categórica derivada | Tipo de ruta según división |
| `mes_creacion` | Numérica | Mes 1–12 |
| `trimestre_creacion` | Numérica | Trimestre 1–4 |
| `dia_semana_creacion` | Numérica | Lunes 0 a domingo 6 |
| `google_distance_km` | Numérica | Distancia terrestre en kilómetros |

Estas 13 variables forman el contrato externo. Todas deben existir en cada solicitud, aunque algunas categorías contengan `__MISSING__`.

### 4.2 Variables utilizadas solo para entrenamiento o validación

- `cost_mxn`: target conocido después de confirmar/realizar el costo.
- Fecha histórica completa: utilizada para cortes temporales y pesos.
- Indicadores de selección de registros.
- Predicciones fuera de muestra y residuales.
- Fold o periodo de validación.

No deben enviarse como features:

- Costo real de la misma operación.
- Venta real.
- Utilidad o margen realizado.
- Facturas.
- Estado posterior del viaje.
- Fecha de entrega o resultado operativo.

Estas variables serían información posterior a la decisión y podrían producir fuga de información.

## 5. Las 16 features consumidas por ONNX

Los ONNX no reciben texto. `preprocessing_state.json` convierte las 13 variables crudas al siguiente tensor, respetando este orden exacto:

| Posición | Feature | Construcción |
|---:|---|---|
| 1 | `mes_creacion` | Valor numérico o mediana congelada |
| 2 | `trimestre_creacion` | Valor numérico o mediana |
| 3 | `dia_semana_creacion` | Valor numérico o mediana |
| 4 | `google_distance_km` | Distancia o mediana de entrenamiento |
| 5 | `CLIENTE_key__freq` | Frecuencia histórica congelada |
| 6 | `PROVEEDOR_key__freq` | Frecuencia histórica congelada |
| 7 | `ORIGEN_key__freq` | Frecuencia histórica congelada |
| 8 | `DESTINO_key__freq` | Frecuencia histórica congelada |
| 9 | `route_key__freq` | Frecuencia histórica congelada |
| 10 | `Tipo de Equipo_key__freq` | Frecuencia histórica congelada |
| 11 | `DIVISION_key__freq` | Frecuencia histórica congelada |
| 12 | `RANGO_key__freq` | Frecuencia histórica congelada |
| 13 | `route_type__freq` | Frecuencia histórica congelada |
| 14 | `distance_log1p` | `log1p(max(distancia,0))` |
| 15 | `ORIGEN_key__te` | Target encoding suavizado del origen |
| 16 | `DESTINO_key__te` | Target encoding suavizado del destino |

Para una categoría desconocida:

- La frecuencia cae a `0`.
- El target encoding cae al prior global congelado.

El sistema debe registrar categorías desconocidas porque una predicción puede generarse, pero tendrá menor soporte histórico.

## 6. Preparación desde la base original

`prepare_quote()` acepta una fila recuperada por el software desde la base original.

Campos y alias admitidos:

| Concepto | Nombres admitidos |
|---|---|
| Cliente | `CLIENTE`, `client`, `customer` |
| Proveedor | `PROVEEDOR`, `provider`, `carrier` |
| Origen | `ORIGEN`, `origin`, `origin_name` |
| Destino | `DESTINO`, `destination`, `destination_name` |
| Equipo | `Tipo de Equipo`, `tipo_equipo`, `equipment` |
| División | `DIVISION`, `division` |
| Rango | `RANGO`, `range` |
| Fecha | `FECHA CREACIÓN`, `FECHA CREACION`, `created_at`, `quote_created_at` |
| Distancia | `google_distance_km`, `distance_km`, parámetro explícito o caché |

### Normalización

1. Convertir texto a minúsculas.
2. Eliminar espacios iniciales/finales.
3. Reducir espacios múltiples a uno.
4. Eliminar acentos mediante Unicode NFKD.
5. Conservar letras ASCII, números, espacios y `, . / # -`.
6. Convertir categorías vacías a `__MISSING__`.
7. Mantener la dirección origen → destino.

Ejemplos:

```text
"  MÉXICO   D.F. "  -> "mexico d.f."
"DryVan   53"       -> "dryvan 53"
None                 -> "__MISSING__"
```

### `route_type`

```python
{
    "national": "national",
    "crossborder": "crossborder",
    "domestic": "domestic",
    "port freight": "port_freight",
}
```

Una división desconocida recibe `pendiente_validacion`. El sistema debe advertir o solicitar revisión para divisiones fuera del soporte conocido.

### Fecha y zona horaria

El día de semana sigue la convención Python/pandas:

```text
lunes=0 ... domingo=6
```

Si la fecha no se proporciona, el preprocesador usa el tiempo del proceso. En producción se recomienda enviar explícitamente el timestamp de creación y definir `America/Mexico_City` en el software anfitrión.

## 7. Caché de rutas

`RouteCache` carga `data/google_maps_route_cache.csv` una vez y consulta rutas normalizadas.

Puede devolver:

- Distancia en kilómetros.
- Coordenadas.
- Elevaciones.
- Fecha de actualización.

Solo utiliza filas con `api_status=OK` y distancia finita no negativa.

```python
from vax_lightgbm import RouteCache

cache = RouteCache()
distance_km = cache.lookup_distance_km(origen, destino)
```

Si la ruta no existe, genera `RouteNotFoundError`. El software debe consultar su proveedor geográfico y pasar la distancia:

```python
prepared = prepare_quote(raw_quote, distance_km=910.5)
```

La copia CSV es adecuada como fuente beta de solo lectura. Para múltiples instancias o actualizaciones concurrentes:

1. Migrar el caché a base de datos o servicio compartido.
2. Usar `route_key` como clave única.
3. Guardar fuente y fecha de actualización.
4. Validar distancia contra origen/destino.
5. Evitar escrituras simultáneas al CSV.

La distancia es crítica: en la validación histórica, el MAE aumentó aproximadamente de MXN 5,942 a MXN 13,256 cuando faltaba.

    "CLIENTE": "Cliente ejemplo",
    "PROVEEDOR": None,

    "DESTINO": "Ciudad de México",

## 10. Semántica exacta del ensemble ONNX

Cada ONNX devuelve una predicción en escala logarítmica. El cálculo correcto es:

```text
log_seed_42   ─> expm1 ─> max(0) ┐
log_seed_2026 ─> expm1 ─> max(0) ├─> promedio en MXN
log_seed_9001 ─> expm1 ─> max(0) ┘
```

Formalmente:

```python
seed_mxn = [max(expm1(output), 0) for output in onnx_outputs]
cost_mxn_prediction = mean(seed_mxn)
```

No usar:

```python
expm1(mean(onnx_outputs))
```

Esa operación no es matemáticamente equivalente y produciría resultados distintos.

## 11. Salidas

| Campo | Descripción |
|---|---|
| `cost_mxn_prediction` | Costo central promedio en MXN |
| `seed_std_mxn` | Desviación entre las tres semillas |
| `risk_range_low_mxn` | Límite técnico inferior truncado en cero |
| `risk_range_high_mxn` | Límite técnico superior |
| `seed_42_prediction_mxn` | Predicción individual |
| `seed_2026_prediction_mxn` | Predicción individual |
| `seed_9001_prediction_mxn` | Predicción individual |
| `model_version` | Versión ONNX para trazabilidad |
| `trained_through` | Última fecha del entrenamiento |

El intervalo técnico utiliza:

```text
semiamplitud = residual_q95_mxn + 1.645 × seed_std_mxn
```

El Q95 se encuentra en `model_manifest.json` y `uncertainty.csv`. Es un rango conservador basado en error histórico; no garantiza el costo de una operación individual.

## 12. Integración en otros lenguajes

Para .NET, Java, Node.js, C++, Rust u otro runtime:

1. Implementar las reglas de `preprocessing.py`.
2. Leer `preprocessing_state.json`.
3. Construir las 16 features en el orden de `features`.
4. Convertir el lote a `float32` con forma `[N,16]`.
5. Cargar las tres sesiones ONNX una sola vez.
6. Ejecutar el input `features`.
7. Aplicar `expm1`, recorte y promedio.
8. Calcular la desviación entre semillas y el intervalo técnico.
9. Persistir la versión del manifiesto.

El manifiesto contiene hashes SHA-256. El integrador debe verificarlos antes de cargar artefactos distribuidos por red o almacenamiento externo.

## 13. Validación de paridad contra joblib

La conversión se comparó con el bundle original en 500 registros que incluyeron:

- Categorías observadas.
- Categorías desconocidas.
- `__MISSING__` y `None`.
- Meses, trimestres y días diferentes.
- Distancias 0, 1, 50, 250, 900, 2,500 y 5,000 km.
- Comparación individual de cada semilla.
- Costo central e intervalo técnico.

Resultados:

| Métrica de paridad | Resultado |
|---|---:|
| Registros | 500 |
| Diferencia absoluta máxima | MXN 0.4695 |
| Diferencia relativa máxima de predicción | 0.000701% |
| Umbral absoluto | Menor a MXN 1 |
| Umbral relativo | Menor a `1e-4` |
| Estado | PASS |

Las diferencias provienen principalmente de la entrada `float32` y son materialmente irrelevantes frente al MAE histórico.

El modelo ONNX también pasó `onnx.checker` para los tres archivos.

## 15. Lógica de la interfaz experimental anterior

La interfaz previa añadía reglas que no están dentro de ONNX:

### Campos obligatorios

- Origen.
- Destino.
- Tipo de equipo.

Cliente, proveedor y rango podían estar vacíos.

### Distancia

Primero consultaba el caché y luego un proveedor geográfico. Sin distancia válida no debería emitirse precio firme.

### Venta sugerida

```text
venta = costo_predicho / (1 - margen_pct / 100)
```

El 18% inicial era una regla de la interfaz, no una salida aprendida.

### Banda comercial

Se mostraba una banda variando ±2 puntos porcentuales el margen. Representa flexibilidad comercial y no intenta contener el costo real.

### Estados por historial

| Condición | Estado previo |
|---|---|
| Ruta sin historial | `requiere_validacion` |
| Menos de cuatro registros o proveedor vacío | `provisional` |
| Historial suficiente | `lista_para_revision` |

El software nuevo necesita consultar la base original y construir la misma `route_key` para reproducir estos estados.

### Confianza y duración

Las etiquetas baja/media/alta no eran probabilidades calibradas. La duración, descansos y velocidad provenían de otro módulo y no son necesarios para el modelo ONNX.

## 16. Reglas operativas recomendadas para la beta

Solicitar revisión humana cuando exista:

- Ruta nueva o con poco historial.
- Distancia faltante, inválida o desactualizada.
- Categoría desconocida.
- Equipo con poca representación.
- LTL, Pipa, Hazmat u operación especializada.
- Port Freight con condiciones no representadas.
- Desacuerdo elevado entre semillas.
- Predicción o distancia fuera del soporte conocido.
- Proveedor sin confirmar al intentar comprometer precio.

No establecer umbrales monetarios automáticos hasta completar validación por bandas de costo.

## 17. Integración con la base original

La conexión SQL, credenciales y consultas pertenecen al software anfitrión. Separación recomendada:

```text
Base original
├── cotización actual ──────> prepare_quote ─> ONNX
├── historial route_key ────> estado operativo
└── costo confirmado futuro ─> monitoreo
```

La consulta para predecir nunca debe incluir el costo real de la misma operación.

## 18. Concurrencia y escalabilidad

- Crear un singleton `ONNXLightGBMPricingModel` por worker.
- Crear un singleton `RouteCache` por worker.
- ONNX Runtime mantiene tres sesiones; no recrearlas por solicitud.
- Usar lotes cuando se procesen varias cotizaciones.
- Cada worker tendrá sus propias sesiones y memoria.
- Definir límites de tamaño y tiempo para lotes.
- Mantener artefactos privados, inmutables y versionados.
- Migrar el caché CSV antes de escrituras concurrentes.
- Implementar health check que valide versión y sesiones cargadas.
- Mantener rollback al deployment joblib o a una versión ONNX anterior.

- Sesgo.
- Tasa y severidad de subestimación.
- Error P90/P95.
- Cobertura y ancho del intervalo.
- Rutas nuevas.
- Distancias faltantes.

## 21. Seguridad

- No exponer ONNX, JSON de preprocesamiento o caché al navegador.
- Mantener credenciales fuera del deployment.
- Verificar hashes del manifiesto.
- Autenticar empleados.
- Validar tipos, longitud de textos y tamaño de lotes.
- No registrar secretos.
- Restringir acceso a información comercial.
- Mantener versionado y rollback.

## 22. Manejo de errores

| Situación | Acción recomendada |
|---|---|
| Falta origen, destino o equipo | Rechazar solicitud |
| Ruta fuera del caché | Consultar servicio geográfico |
| Fecha inválida | Rechazar y solicitar corrección |
| Distancia negativa | Rechazar |
| Distancia ausente | Bloquear precio firme o marcar provisional |
| Categoría desconocida | Permitir fallback y advertir |
| Artefacto/hash inválido | No cargar instancia |
| Sesión ONNX no inicia | Health check fallido |
| Predicción no finita | No cotizar y registrar incidente |

## 24. Limitaciones

- ONNX reproduce las limitaciones del modelo original.
- El entrenamiento termina en 2025.
- No conoce disponibilidad actual de carrier.
- No observa explícitamente todos los peajes, combustibles, accesoriales o urgencia.
- Rutas nuevas y equipos raros tienen mayor riesgo.
- Las categorías nuevas usan fallbacks globales.
- El intervalo es conservador y no está calibrado perfectamente por segmento.
- El modelo estima costo; margen y decisión comercial permanecen fuera.

## 26. Criterio de éxito de la beta

El éxito no se limita a que ONNX ejecute correctamente. Debe demostrar que:

- Reduce el tiempo de cotización.
- Mantiene o mejora el margen realizado.
- Controla subcotizaciones graves.
- No deteriora materialmente la conversión.
- Produce overrides explicables.
- Mantiene estabilidad por división, ruta y equipo.
- Puede revertirse rápidamente.

La promoción requiere evidencia prospectiva y aprobación de Ventas, Operaciones, Procurement y Finanzas.
